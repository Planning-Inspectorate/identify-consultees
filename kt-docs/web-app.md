# Web app

`apps/manage`: Express, Nunjucks and GOV.UK Frontend on Node 24. Pages are server-rendered. Client JS only enhances them, mainly the maps.

## Layout

```
apps/manage/
  src/
    server.ts          # listen, trust proxy
    app/
      app.ts           # createApp: static assets, security headers, Nunjucks, router
      router.ts        # mounts feature routers (dev pages behind devPagesEnabled)
      config.ts        # env → typed config
      service.ts       # ManageService: db, logger, rulesetRunner, blob client
      maps/            # static map render, cache and serve; Defra vendor assets; results map config
      views/           # one folder per feature: index.ts router, controller, view-model, view.njk
      security/        # CSP and header helpers
      sass/            # GOV.UK and PINS overrides
    util/              # build, asset fingerprinting, static middleware, inline JSON
  public/              # client JS and images, fingerprinted into src/.static
  e2e/                 # Playwright journeys (need the seeded local database)
```

A request goes: `server.ts` → `createApp` → `buildRouter` (monitoring, `/vendor/*`, auth, then features) → a controller that queries `packages/database` or the Python function through `service`, builds a view model and renders Nunjucks. Map page config goes into the page as `<script type="application/json">` (`util/inline-json.ts`) and the client JS finds its containers by class.

## The journey

1. Search on `/` and pick a project. Links use the case boundary's id: `resolveCase` 404s anything that isn't a UUID without touching the database. A case reference (`EN010025`) isn't unique, because a project can have several boundary files.
2. The project boundary page draws every stored shapefile as a toggleable "GIS shapefiles" map layer, all visible to start with (and all on its static image), each styled by how recent it is; the radios below confirm the single file carried into the report. Picking a different real file continues the journey under that submission's own id. A file's geometry that fails to load leaves the radios working but swaps the map for a notification banner — "There's a problem loading the map – try again later" — with a Try again link back to the same page.
3. _Continue_ leads to the ruleset radios; _Identify consultees_ leads to the check page: report details (project, reference, shapefile, ruleset — each with a _Change_ link) and each category's consultee names, capped at 10 with a "Showing 10 of N" note beyond that.
4. A category's **Change** link lists its consultees. _Remove_ opens a page that takes the removal reason, then adds `exclude=<json>` (`{"i":consulteeAreaId,"c":category,"n":name,"r":reason}` — a hand-added consultee's entry has no `i`, its `add` param is dropped) to the URL and returns with the **Removed consultees** section open. Below the table, the **Add consultee** link opens the Add a consultee page: a name and a reason (both required, mirroring the removal reason), posting back to itself; errors show on the same page. As the name is typed, the GOV.UK accessible autocomplete (`public/javascripts/consultee-autocomplete.js`; a native `datalist` without JavaScript) suggests the category's consultees the page removed, marked "removed", then those only the nearby search found (the faint ones on its map), nearest first, with their distance - for Nearby NSIPs, every other case instead (`findOtherCases`), each named "project name (reference)", a removed one marked so. Adding a removed consultee back undoes its removal: it returns as the ruleset found it, identified and drawn as such, not as added by hand (the reason typed isn't kept). The name has to be a real consultee of the category: the server matches it (case and spacing aside) to the nearest suggested name - for a Nearby NSIP, to a case by its "project name (reference)", its project name alone or its reference alone - else, for a consultee category, to the nearest of that name anywhere in the reference data (`findConsulteeAreaByName`). Any other name - a typo, or a made-up one - is refused with "Consultee not found", as is a name already listed in the category. It then adds `add=<json>` (`{"i":consulteeAreaId,"c":category,"n":name,"r":reason}`) and returns to the category page. A nearby consultee is drawn on the maps as identified (the static map's `include` param carries it); one further away isn't on the maps, but the report has its stored row. Links from before this check may still carry adds with no `i`; they're listed, with no area to draw. A bare `exclude=<consulteeAreaId>` still excludes (the static map's links use it) but lists no reason. There's no server-side state, so the lists and rows always agree (`report/urls.ts`). Each `add` and `exclude` entry travels **base64url-encoded** (`eyJ…`): Front Door's firewall scores plain JSON in a query string as an injection attempt and blocks the page ("The request is blocked."). Links carrying plain JSON, from before, still read. For the same reason the firewall leaves the add and remove forms' free-text `name` and `reason` fields out of its checks (`infrastructure/front-door.tf`).
5. _Create report_ carries the same parameters to the created page, which builds the report then and there: the consultees the ruleset's conditions identified, less removals, plus additions. Consultees only the nearby search found are never in the report; the category pages' maps show them fainter, as context, and the report's PDFs leave them out.
6. The created page's download link serves the ZIP it just built - kept in memory under its URL, for the user who built it (its Summary names them), so the link can give the file's size - or builds it again if that's gone: an Excel workbook, and a PDF of each category in the report's map (`maps/NN <category>.pdf`), with a key and the category's consultees listed with why (`consultees/reasons.ts`). Each map draws only the category's consultees in the report - each named on it, where labels have room without overlapping (a name already on the map isn't repeated) - over a greyscale basemap, with the ruleset's buffers for the category drawn dashed around the site and keyed: the distance of each condition that finds the category within a buffer (Ambulance Trust: 1km and 10km), or `nsipRadiusKm` for Nearby NSIPs; conditions that need an area to touch or border the site have none. The buffers grow from what the run screened - the site's outline, or its bounding box (`screenedSite`) - and each map frames the bounding box of what it's about - the site, its buffers and the category's local areas in the report (not regional ones, which would lose the site), 5% around it - at the exact zoom that fills it (`reportMapView`), or with nothing but the site to frame, the site with the category's `mapKm` around it. The maps are drawn at 1.5 image pixels per map pixel, so they're sharp printed or zoomed in. The labels need a font, which the app's image installs (`font-dejavu` in `apps/manage/Dockerfile`; Alpine has none). The workbook has a **Summary** tab - the project, case reference, boundary file and when it was received, the ruleset (and, only when the run screened the site's bounding box, a warning that the list can include consultees that aren't near the site), when the report was generated, and **Report generated by** - left blank and highlighted yellow, for whoever sends the report to fill in, each tab's total followed by a line per category under the label `summary` gives it in [`config/report.yaml`](../config/report.yaml) (in that order, shown at 0, categories sharing a label sharing a line; any other category with consultees under its own name), the overall total, how many the ruleset identified, were added and removed, then the added and removed consultees with their reasons, and the **List of National infrastructure projects** (the NSIPs: those found, nearest first, then those added by hand - each one's Name, Number (case reference), Type, Sub-type and Query: "35km buffer", or the reason it was added) - then a tab per ruleset **Group** (Administrative boundaries, Public bodies, Energy, Transport, Other) listing each consultee with the columns [`config/report.yaml`](../config/report.yaml) sets for the tab: its fixed columns (Consultee, Category, Why identified and Source on every tab; Subcategory and Distance from site on Energy and Transport), then the metadata attributes its categories list, under readable headings (Code, Official name, Operator, Technology...). Attributes with the same heading share a column, attributes not listed are left out, and a consultee without one leaves its cell blank. Settings are set by default, for a tab, and for a category on it; a category belongs to the tab its group in `config/reference-data.yaml` is named for. Each consultee goes on the tab of the condition that identified it; a hand-added one, on its category's (a matched nearby one with its stored row), its Source "Manually added". A category can have a Summary line for each buffer its conditions find it within - Ambulance Trusts within 1km, and within 10km - each consultee counted on its nearest. The last tab is **NSIPs** (see below).

**Nearby NSIPs** are the other cases near the site, treated as another consultee category whose data sits in `case_boundary` rather than `consultee_area` (`views/consultees/nearby-nsips.ts`). Each run adds them to the ruleset's consultees: every case with a boundary within [`config/nearby-consultees.yaml`](../config/nearby-consultees.yaml)'s `nsipRadiusKm` (35km; 0 turns them off) of the site, once each by its most recently received shapefile, never the site's own case (`findNearbyCases`). They're named "project name (reference)", identified as "Another NSIP within 35km of the site", and are report content like a condition's matches (`isIdentified`): the check page lists them last under their own heading (their row shows while they're looked for, found or not), their Change page maps and lists them with the usual Remove and Add - the Add a consultee page suggesting the other cases, nearest first, since every nearby NSIP is already listed - and the download has an **NSIPs** tab - each case's Name, Number, Type, Sub-type and Query, the same as the Summary's list (`nsipFields`). The report calls them NSIPs throughout - category, tab and map. Type and sub-type come from the case reference - its Planning Act sector and sub-sector, as in TR01 (Transport, Highways) - so every case has them, from a file or from CBOS (`nsipType`; Business and Commercial cases get a type alone), from its `case_boundary` row - and a `maps/NN Nearby NSIPs.pdf`. Their map draws each case's boundary from `case_boundary.geometrySimplified`, simplified further for display; the distance is measured on it too (within 10m of the original). Their Change page frames its map as `config/report.yaml` sets for the tab `Nearby NSIPs` (35km, as far as `nsipRadiusKm` looks); change both together. Since the maps' search area reaches the largest nearby distance, `nsipRadiusKm` sets it too (35km, over the consultees' 20km).

The report pages, their maps and the download share one ruleset run: the first to need it runs it and keeps it in the session (`runRulesetSafely`), without geometry or metadata, for an hour; a different case or ruleset replaces it. Nothing is stored beyond the session, except the built reports themselves: the created page keeps each one it builds in process memory, under its download URL, for up to an hour (the few newest only), so the download link can serve it straight away. Only the first page waits for the function (about 5s on a full data load), and the created page waits for the report's maps to build.

The case maps (category pages and static images; the report's PDFs frame their own) open on the site with the category's `mapKm` around it ([`config/report.yaml`](../config/report.yaml)), and the boundary page's map on the shapefiles with `boundaryMapKm` ([`config/map-view.yaml`](../config/map-view.yaml)) around them - fitted to the 960x516 map in Web Mercator at the closest whole zoom (`computeFittedMapView`). That zoom is on 256px raster tiles, as the static images draw; the interactive map (MapLibre, 512px tiles) opens one level lower, which shows the same area (`interactiveZoom` in `consultees-map.js`). The interactive maps zoom out for the rest. Static images leave out path points beyond the map's edges (`visiblePathPoints`), so regional areas don't run to megabytes at that zoom.

If the ruleset can't be run (function down, timeout, bad key) the pages say so instead of showing an empty list. With no database the search shows an empty list and logs the error.

## Admin section

Internal tools for loading and checking an environment's data, all in `apps/manage/src/app/admin/`: one folder per page, a layout with a menu between them (`admin/layout.njk`, the list in `admin/navigation.ts`), and their tests. `createAdminRoutes` mounts them under `/admin`; `adminHeaderLink` adds **Admin** to the header. To add a page, add its folder, a route in `admin/index.ts` and an entry in `ADMIN_PAGES`. To take the section out of the service, delete the folder, the lines in `router.ts` and `app.ts` (and `testing/create-test-app.ts`) that import from it, and its paths in the `e2e/` page lists.

## Auth

`AUTH_DISABLED=true` locally. Otherwise `/auth` is rate limited and everything after it needs an Entra login and group membership (`authGuards`). Footer pages and monitoring stay public.

## Changing the case or ruleset shape

Update the `home` and `consultees` view models, the unit tests beside them, and `e2e/fixtures.ts` (`SAMPLE_CASE_ID`, `SAMPLE_RULESET_ID` come from the dev seed).
